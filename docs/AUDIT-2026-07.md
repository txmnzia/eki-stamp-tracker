# Codebase audit & remediation plan — July 2026

Full audit of the Eki Stamp Tracker: app (`index.html`), UAT build (`uat/`),
data pipeline (`scripts/`), and the shipped data files (`data/`). Every finding
below was verified against the actual code/data (file:line references are to
the current `main`, commit `ecea323`). Findings are grouped into remediation
**blocks** ordered by implementation priority; each block lists its findings
with severity, evidence, and a concrete fix.

**Severity scale**
- **P0 Critical** — active security/data-safety exposure; fix before anything else.
- **P1 High** — real user-visible data loss, broken core features, or corruption risk.
- **P2 Medium** — functional defects, inconsistencies, doc/code drift.
- **P3 Low** — polish, a11y, dead code, hygiene.

---

## Executive summary

The app is impressively engineered for a single-file project — the ride-geometry
work (stitching, corridor filtering, graph routing) is genuinely sophisticated
and the data files are largely clean (all 22,016 geojson features valid, all
10,452 station codes unique, referential integrity between `stamp-stations` and
`stations` holds for every non-null key). But the audit found:

1. **One critical security flaw**: a GitHub PAT is embedded in the public page,
   deliberately obfuscated to evade GitHub's secret scanner. It gives anyone
   read/write access to *every* user's synced data and is the app's only
   authentication.
2. **Three high-severity data-loss paths in the sync UX** (anonymous progress
   evaporates on refresh; "Load session" silently destroys unsaved local
   progress; the UAT build writes into production Gists).
3. **One high-severity race** that corrupts ride overlays for returning users
   (geometry built and cached mid-render — the repo's own audit script works
   around exactly this bug, but the app itself doesn't).
4. **84 curated stamp stations that can never appear in the app** (they exist in
   `stamp-stations.json` with names and coordinates, but the render path only
   draws stations joined to ekidata by `eki_code`).
5. A cluster of consistency bugs: unversioned line cache contradicting the
   README, a UAT experiment left half-alive (with a regeneration script that
   silently overwrites the *production* geojson), bilingual display gaps, and
   literal HTML entities shown to users.

## BLOCK 0 — Security: kill the shared token model  *(P0 — do first, independent of everything else)*

### 0.1 Embedded GitHub PAT, obfuscated to evade secret scanning — **P0 Critical**
`index.html:988–1007` (`GH_TOK_OBF`, `decTok`, and the comment explaining the
scheme; duplicated at `uat/index.html:993–1012`).

A classic GitHub PAT is baked into the page as XOR'd char codes, explicitly so
that "GitHub's secret scanner won't see (and auto-revoke) it". Consequences:

- Anyone can decode it in one line (the page even ships `encTok`/`decTok` and
  documents the procedure in a comment).
- The token lists **all** gists of its owner account → every user's "private"
  sync gist is enumerable, readable, writable, and deletable by anyone.
  `findGistId` (`index.html:1157–1169`) works precisely because the token can
  list everything.
- All users share one token → one shared GitHub API rate limit (5,000 req/h);
  `findGistId` paginates through the *entire* gist list per new device, so the
  ceiling shrinks as the user base grows.
- Sync names are the only "credential" (`GIST_PREFIX + name`), so knowing or
  guessing a sync name is full read/write on that user's data even without
  decoding the token.
- If GitHub ever detects and revokes the token (or the account is flagged for
  scanning evasion), sync breaks for every user simultaneously.

**Fix (ordered):**
1. **Revoke the current token immediately** (it is compromised by definition).
2. Choose a replacement persistence model. Realistic options for a
   static-hosting app, in order of recommendation:
   - **(a) Per-user token (BYO gist)** — each user pastes their own `gist`-scope
     PAT once; store it in `localStorage`. Zero shared infrastructure, real
     isolation, no rate-limit sharing. Cost: a one-time setup step in the
     welcome modal.
   - **(b) Tiny sync proxy** (Cloudflare Worker / Vercel function, ~50 lines)
     holding the token server-side, keyed by a random per-user secret issued at
     first sync (stored in `localStorage` and shown as a "recovery code").
     Keeps the current zero-setup UX, fixes enumeration and rate-limit sharing.
   - **(c) Drop remote sync**; local-first (IndexedDB) + export/import files.
     Simplest and honest, loses cross-device sync.
3. Whatever the choice, **delete the `encTok`/`decTok` machinery** and never
   re-embed a shared credential.
4. Migration: on first load of the new version, offer a one-time "export your
   data" path so existing users can carry progress over.

### 0.2 Latent XSS from scraped data — **P2 Medium** (bundled here because it's the other security item)
`buildPopupHtml` (`index.html:2370–2408`), `buildLinePopupHtml` (`1362–1377`),
and the ride tooltip (`1384`) interpolate station/line names into `innerHTML`
and attribute values without escaping. Names originate from a **scraped
external site** (`scrape_funakiya.py` regex-extracts HTML titles), so a
malicious or compromised upstream page becomes script execution in every
user's browser at next data regen. The search suggestions already do this
right (`textContent`, `2687–2695`).

**Fix:** add a tiny `esc()` (HTML-entity escaper) and apply it to every
interpolated name/attribute in the three popup/tooltip builders. ~10 lines.

## BLOCK 1 — Stop losing user data (sync/session UX)  *(P1 — highest user impact after security)*

### 1.1 Anonymous progress is silently lost on refresh — **P1 High**
Stamps/rides live only in `state` (memory) and the Gist. If the user clicks
"Skip for now" on the welcome modal (`index.html:2979`) and starts collecting
(the stats bar actively invites them: "tap any station to begin"), a reload
discards everything. `scheduleSave → syncToGist` returns immediately when
`state.user` is empty (`1192`). Nothing persists locally.

**Fix:** persist `state.stamps`/`state.rides` to `localStorage` (or the
existing IndexedDB store) on every mutation, and hydrate from there at boot
when no session is set. ~20 lines, no design change.

### 1.2 "Load session" destroys unsaved local progress — **P1 High**
`session-load` (`index.html:2845–2855`) and the welcome-modal confirm
(`2966–2976`) call `loadFromGist(name)`, which **replaces** `state.stamps` and
`state.rides` with the remote content — including with an *empty* set when the
name has no gist yet (`1176`). The natural "claim my anonymous progress" flow
(collect → open session panel → type a name → Load) therefore wipes the very
progress the user is trying to save.

**Fix:** when local unsynced progress exists and the loaded gist differs,
**merge** (union stamps; union ride segment keys per line) or at minimum
prompt ("Keep 12 locally collected stamps?"). Merging is safe here because
both stores are sets of stable keys.

### 1.3 Debounced save races a session switch — **P1 High**
`loadFromGist` sets `state.gistId` **before** awaiting the gist fetch
(`index.html:1177–1178`) and never cancels a pending `syncDebounce`. Sequence:
collect a stamp (schedules save in 2 s) → load session B → `state.gistId`
becomes B's id → debounced `syncToGist` fires mid-load → **user A's stamps are
written into user B's gist** (then the fetch result overwrites local state, so
the corruption is remote and invisible). Same-name-different-device variants
of this race can also interleave `PATCH`es.

**Fix:** `clearTimeout(syncDebounce)` at the top of `loadFromGist`; set
`state.gistId` only after the content fetch succeeds; guard `syncToGist` with
an in-flight/session token so a stale debounce can't write across sessions.

### 1.4 Cached gist id is never invalidated — **P2 Medium**
`findGistId` caches `eki_gist:<user>` in `localStorage` forever (`1159–1165`).
If the gist is deleted (user cleanup, token rotation), every subsequent
`loadFromGist`/`syncToGist` 404s → permanent "✗ sync error"; retry re-uses the
same dead id. **Fix:** on a 404 for a cached id, drop the cache entry and re-run
discovery (create-on-save already handles the rest).

### 1.5 "Reset all stamps" leaves rides behind — **P2 Medium**
`session-reset` clears only `state.stamps` (`2930`). Export/import and the
gist payload treat stamps+rides as one dataset; reset doesn't. Either rename
the button ("Reset stamps") or (recommended) clear both after the two-step
confirm, and say so in the confirm label.

### 1.6 Import silently overwrites the cloud copy — **P3 Low**
Import (`2882–2909`) replaces state then immediately `syncToGist()`s, with no
"you're about to replace 812 synced stamps with this 40-stamp file" guard.
Add a count-delta confirm before the remote write. Also validate the `rides`
shape on import/load (each value an array of strings) — a malformed value
currently throws inside `renderRideOverlays` (`codes.flatMap`, `2053`) and
breaks all subsequent overlay rendering.

## BLOCK 2 — Ride-overlay correctness  *(P1 — core feature renders wrongly)*

### 2.1 Geometry built & cached mid-render corrupts overlays — **P1 High**
Line features render in RAF batches over several seconds
(`renderLines`, `index.html:1567–1605`; 22k features / 150 per frame). For a
returning user, `loadFromGist` typically resolves mid-render, and init then
calls `renderAllRideOverlays()` (`3038–3042`), which calls
`buildLineGeometry(name, seed)` — reading `linesByName[name]` **while it is
still partially populated** — and stores the result in `lineGeomCache`
(`1964`). The poisoned entry is reused by the post-render
`onLinesReady → renderAllRideOverlays` pass (`1635`) *and* by ride-edit mode,
so overlays show phantom gaps / wrong routing until a full reload with warm
cache. The repo already knows about this failure mode:
`scripts/audit-ride-gaps.mjs:41–50` explicitly waits for rendering to settle
"— building geometry mid-render caches an incomplete graph and reports false
gaps". The app has no equivalent guard.

**Fix:** add a `linesReady` flag set in `onLinesReady`. Until it's true,
`renderAllRideOverlays`/`enterRideEditMode` should defer (queue the call) —
or, simpler, `lineGeomCache` writes are skipped while `!linesReady`.
Also clear `lineGeomCache` (and `geom._graph`) in `onLinesReady` as a
belt-and-braces reset.

### 2.2 Line-geometry cache ignores `APP_VERSION` — **P2 Medium** *(fix exists in UAT, missing in prod)*
Prod caches the geojson under the bare IndexedDB key `'eki_lines'`
(`index.html:1637,1650`), while the station cache is versioned
(`'eki_stamp_stations_' + APP_VERSION`, `2634,2650`). The README (l.121–123,
301–303) promises that bumping `APP_VERSION` forces fresh data — **false for
track geometry**: clients keep stale lines for up to 7 days after a data ship.
Commit `78ed468` fixed this; the revert `98aedb0` removed it from prod; the
fix survives only in `uat/index.html:1642,1655`. **Fix:** port the
version-suffixed key to prod. While there, garbage-collect stale
`eki_stamp_stations_*` / `eki_lines_*` keys for other versions (currently the
DB grows ~15 MB per release, forever).

### 2.3 Nishi-Kyushu Shinkansen doesn't exist anywhere — **P2 Medium**
`LINE_DATA` advertises it (`'西九州線'`, `index.html:599`) but
`shinkansen.json` has 7 lines (no 西九州新幹線) and the geojson has **zero**
features for it (verified: only 東海道/山陽/東北/上越/北陸/九州/北海道 exist).
The line opened in Sept 2022 — the source geometry predates it. Users cannot
see or log Japan's newest Shinkansen. **Fix:** add it to
`build_shinkansen.py`'s `LINES` (Takeo-Onsen–Nagasaki stops; coordinates are
in `stations.json` for 武雄温泉/嬉野温泉/新大村/諫早/長崎), regenerate, and
accept the smooth-curve fallback until the geojson is refreshed upstream.

### 2.4 Duplicate/conflicting Shinkansen colours — **P3 Low**
`LINE_DATA`'s Shinkansen entries (`592–599`) are dead code with *different*
hexes than the authoritative `shinkansen.json` (e.g. 東北 `#006B3C` vs
`#22B14C`, 北陸 `#E60012` vs `#E4007F`). `drawShinkansen` only uses
`info.color` (`1548`). Delete the dead entries or reconcile the palettes so a
future refactor can't flip colours.

## BLOCK 3 — Decide and dismantle the UAT experiment  *(P1 — live risk while it lingers)*

The homonym-disambiguation experiment (`78ed468` → reverted `98aedb0` →
re-landed as `/uat/` in `4b38df7`) is a **pure data relabelling**: 1,616
features differ from prod, only in `路線名` (geometry byte-identical); the bare
`本線` alone fans out into 19 operator-qualified names, exactly the corridor
the README flags as merging 京成/相鉄/京急. The app code contains no
disambiguation logic; `uat/index.html` diverges from prod by just 6 hunks
(banner, `-uat` version, `../data/` paths, uat geojson, versioned line cache).

### 3.1 UAT shares the production Gist namespace — **P1 High**
`GIST_PREFIX`, `eki_current_user`, `eki_lang`, and `eki_gist:*` keys are
identical in both builds (prod `index.html:1008,1062–1063`; uat
`uat/index.html:1013,1067–1068`). Served from the same origin (as designed), a
user opening `/uat/` with their normal sync name **writes back into their
production gist** — and because rides are keyed by `路線名`, UAT sessions
inject disambiguated keys (`JR日光線`) that are orphaned in prod, while
`syncToGist` does a full-content replace (`1194–1204`). Production ride data
is polluted by design.

### 3.2 `disambiguate_geojson_lines.py` overwrites the PRODUCTION geojson — **P1 High**
The script reads **and writes back** `data/railroad-section.geojson` in place
(`scripts/disambiguate_geojson_lines.py:20,95`) — not the `.uat.geojson` the
commit message claims it regenerates. Running it as documented silently
mutates the live production data file.

### 3.3 Hand-maintained 3,050-line duplicate — **P1 High (maintenance)**
`uat/index.html` only stays correct because `ecea323` was manually ported into
it. The next forgotten port silently invalidates the experiment (or ships a
prod fix nowhere).

**Fix (one decision, then ~an hour):**
- **Accept the disambiguation** (recommended — it fixes the known `本線`/
  `京都線`/`奈良線` ride-gap anomalies the README lists): copy
  `railroad-section.uat.geojson` over `railroad-section.geojson`, write a
  migration for existing ride keys (bare name → operator-qualified, resolvable
  by seeding each saved ride's station centroid against the relabelled
  corridors), bump `APP_VERSION`, then **delete** `uat/`,
  `railroad-section.uat.geojson`, and fix the script's `GEO` path to take
  input/output arguments.
- **Or reject it**: delete `uat/`, the `.uat.geojson` (~14.8 MB), and the
  script.
- **If it must stay longer**: replace the copy with a `?uat=1` runtime flag in
  the single `index.html`, and give UAT a distinct `GIST_PREFIX` + storage keys
  *today*.

## BLOCK 4 — Data quality & bilingual display  *(P2 — wrong/ugly content, all data-pipeline fixes)*

### 4.1 84 curated stamp stations can never be displayed — **P1 High (data)**
84 of 2,411 entries in `stamp-stations.json` have `eki_code: null` (all
defunct JNR / third-sector lines: 北海道ちほく高原鉄道足寄, 国鉄広尾, …). They
carry valid `fk_*` codes, names, and coordinates, but the app only creates
markers from `stations.json` rows joined via `stampNames[s.eki_code]`
(`index.html:2647`), so these stamps are unreachable — the advertised
`count: 2411` overstates the real catalogue by ~3.5%. (16 of them even have
snap entries in `rail-graph.json` under `fk_*` keys — a keying inconsistency
between pipeline outputs.)
**Fix:** in `loadStations`, after the ekidata passes, create markers directly
from `stamp-stations.json` records whose `eki_code` is null (they already have
`lat/lon`, kanji, English); collect-state keys on `s.code` (`fk_*`) work
unchanged through the existing `state.stamps` set.

### 4.2 23 line labels show raw kanji in EN mode — **P2 Medium**
The stamp `.lines` values include 23 kanji names (京成本線 ×34 stations,
JR山陽新幹線 ×20, JR青梅線 ×14, 大阪高速鉄道大阪モノレール線 ×14, …) because
`funakiya-lines.json` lacks their EN mapping, so EN-mode popups show Japanese.
**Fix:** backfill those 26 registry entries (23 kanji + 3 uncovered EN names)
in `funakiya-lines.json` / `CURATED_LINE`, re-run `build_stamp_stations.py`.

### 4.3 Literal HTML entities in displayed names — **P2 Medium**
`JR北陸新幹線（高崎&#65374;上越妙高）` (8 stations' badges) and
`JR Shin&apos;etsu Main Line(…)` (~6 stations + `funakiya-lines.json`
`jr-shinetsu-ueda-line`) render verbatim. **Root cause:** the scrapers never
`html.unescape()` extracted titles (`scrape_funakiya.py:146–164`,
`scrape_funakiya_lines.py:37–44`). **Fix:** add `html.unescape()` at both
extraction points and regenerate; spot-fix the two shipped values meanwhile.

### 4.4 `funakiya-lines.json` is incomplete for 56 lines — **P2 Medium**
28 entries missing `name_kanji`, 29 missing `name_en`. **Root cause:** the
kanji regex in `scrape_funakiya_lines.py:34` requires names to end in `線`, so
ゆりかもめ-style names never match. Loosen the regex (match up to `のスタンプ`)
and regenerate.

### 4.5 18 Shinkansen-only stops can't light stamp badges — **P3 Low**
Synthetic `shk_*` codes (新富士, 岐阜羽島, …) exist in no station record, so
the README's "collected-stamp badges still light up" claim doesn't hold for
them. Expected behaviour; fix the README sentence (or map them to the
funakiya slugs where a stamp actually exists).

### 4.6 One "geographic order" violation — **P3 Low**
`JR成田線` contains a 75.4 km hop (銚子→我孫子): trunk + Abiko branch
concatenated as one ordered list. Already acknowledged in the README's gap
list; worth a comment in the data or a branch-aware split if the corridor
logic ever gets revisited. All other 590 lines order cleanly.

## BLOCK 5 — Pipeline & tooling hygiene  *(P2/P3 — reproducibility and safety of regeneration)*

- **5.1 (P2)** `build_stamp_stations.py`, `build_rail_graph.py`, and both
  scrapers use **CWD-relative paths** (`data/...`), while `build_shinkansen.py`
  and `disambiguate_geojson_lines.py` are ROOT-anchored. Running a scraper from
  `scripts/` writes `scripts/data/*.json` silently. Anchor all of them to the
  repo root like `build_shinkansen.py:19–20`.
- **5.2 (P2)** README's "Regenerating data" section omits two required stages:
  the real order is `scrape_funakiya.py` → `scrape_funakiya_jp.py` →
  `scrape_funakiya_lines.py` → `build_stamp_stations.py` → `build_rail_graph.py`
  → `build_shinkansen.py`. Document it (and the `pykakasi` optional dependency,
  whose silent absence degrades every romanised fallback name).
- **5.3 (P2)** No CI at all: `audit-ride-gaps.mjs` self-describes as a CI gate
  and exits non-zero on gaps, but there is no workflow. Add a GitHub Action
  that serves the repo and runs it (plus a JSON-schema sanity check on the
  data files) on PRs touching `data/` or `index.html`.
- **5.4 (P3)** Scraper caches live in `/tmp/funacache` with no TTL — a stale
  cache silently freezes upstream changes; document or add a `--no-cache` flag.
- **5.5 (P3)** Dead code: `coord` map in `build_shinkansen.py:34` is unused;
  duplicate `"Nankai"` in `OP_PREFIX` (`build_stamp_stations.py:25`).

## BLOCK 6 — UX & accessibility polish  *(P3 — batch when convenient)*

- **6.1** Search suggestions have `role="listbox"`/`role="option"` but no
  keyboard navigation (no arrow keys, no `aria-activedescendant`, Enter does
  nothing) — `index.html:2664–2725`. Add ↑/↓/Enter/Escape handling.
- **6.2** Search only matches **stamp** stations (`markers`, `2671`); the ~6.7k
  plain stations are invisible to search with no hint. Either include them
  (badged "no stamp") or say "Search stamp stations…" in the placeholder.
- **6.3** `#session-panel` uses a fixed `top: 56px` (`176`) while the topbar is
  safe-area-offset (`88`) — on notched phones the panel overlaps the topbar.
  Use `top: calc(env(safe-area-inset-top, 0px) + 56px)`.
- **6.4** `document.documentElement.lang` is only set when toggling language
  (`2745`), not at boot — a stored `jp` preference leaves `<html lang="en">`
  for screen readers. Set it during init.
- **6.5** Escape in the ride editor (`2280`) fires even while typing in the
  search box; scope it (`e.target` check). The welcome modal's focus trap
  hides the overlay on Escape without returning focus.
- **6.6** Canvas markers are unreachable by keyboard entirely — acceptable for
  a touch-first map, but worth a line in the README's conventions.
- **6.7** In-page texts (welcome modal, session panel, hints, toasts) stay
  English in 日本語 mode. README only promises bilingual *names*, but the
  welcome modal title already switches (`2956`) — either finish the job for
  the small set of UI strings or drop the title toggle for consistency.
- **6.8** `findGistId`'s unbounded pagination happens on the UI path (session
  load) with no feedback beyond "Loading…" — after Block 0 this likely
  disappears; otherwise add a spinner state.
